# SatQuery — SIH26167 Backend Implementation Blueprint

## Purpose

This document is the **implementation-level backend plan** for SatQuery.

It is intentionally more detailed than a feature checklist. It tells the backend developer:

- what to build
- why it exists
- how the components should communicate
- what APIs to create
- what database entities to store
- what data should be dynamic
- how the AI/agent layer should work
- how satellite images should be processed
- how Optical + SAR fusion should work
- how bi-temporal change analysis should work
- how evidence and confidence should be represented
- how to evaluate the system
- how to make the backend reliable enough for an SIH demonstration

> **Important:** Implement only claims that the actual system can demonstrate. Do not put "fine-tuned", "multimodal", "agentic", "real-time", or benchmark numbers in the PPT unless the backend genuinely implements and measures them.

---

# 1. Core Product Goal

SatQuery should behave like a **remote-sensing analysis agent**, not like a normal chatbot with an image upload.

The target interaction is:

```text
User
 |
 | natural-language request
 v
SatQuery API
 |
 v
Planner / Intent Router
 |
 +-----------------------+
 |                       |
 v                       v
Single-image task     Multi-image task
 |                       |
 +-----------+-----------+
             |
             v
      Specialist tools
             |
   +---------+----------+
   |         |          |
   v         v          v
  VQA     Change     Optical/SAR
 Model    Model        Fusion
   |         |          |
   +---------+----------+
             |
             v
       Evidence Layer
             |
             v
       Result Validator
             |
             v
       Final Response
             |
       +-----+------+
       |            |
       v            v
    Answer       Evidence
                    |
                    v
                  Trace
```

The system should automatically decide whether a request requires:

- single-image VQA
- captioning
- grounding
- bi-temporal change analysis
- Optical + SAR fusion
- metadata/geospatial analysis
- multiple tools in sequence

# 11. Model Registry

The model registry prevents hard-coded model selection throughout the codebase.

Example:

```json
{
  "name": "satquery-vqa",
  "version": "1.0.0",
  "task": "single_image_vqa",
  "modalities": ["optical"],
  "device": "cuda",
  "status": "ready"
}
```

Python interface:

```python
class BaseModel:

    name = ""
    version = ""
    task = ""

    def load(self):
        raise NotImplementedError

    def predict(self, inputs, parameters):
        raise NotImplementedError

    def health(self):
        return True
```

Every specialist model must follow this interface.

# 18. Change Pipeline — Detailed Implementation

## Step A — Validate

Check:

```text
two inputs exist
both are readable
compatible spatial information
compatible dimensions where expected
```

## Step B — Align

If geospatial metadata exists:

```text
CRS normalization
 ↓
reprojection if required
 ↓
resampling
 ↓
co-registration
```

If images are already aligned, skip unnecessary transformations.

## Step C — Preprocess

Apply consistent:

```text
normalization
band selection
resolution handling
cloud/no-data handling
```

## Step D — Detect change

Possible approaches:

```text
pixel difference
spectral difference
feature difference
deep change-detection model
segmentation/change model
```

Use the strongest reproducible method available to the team.

## Step E — Create mask

Output:

```text
0 = unchanged
1 = changed
```

Then post-process:

```text
remove tiny noise regions
connected components
region filtering
```

## Step F — Quantify

Calculate:

```text
changed pixel count
changed area
percentage changed
region count
```

Only calculate physical area when spatial resolution/georeferencing makes that calculation meaningful.

## Step G — Semantic interpretation

Feed change evidence to the semantic model:

```text
change regions
before image
after image
question
```

Output:

```text
construction
vegetation loss
water expansion
road development
etc.
```

Do not force a class when evidence is insufficient.

The planner should convert natural language into a **structured execution plan**.

Example user query:



# 27. Planner Must NOT Return Arbitrary Code

Never execute model-generated Python or shell commands.

The planner should only select from an allow-listed tool registry.

Allowed:

```text
vqa_model
change_detector

fusion_model

evidence_generator
```

Not allowed:

```text
execute_python

```

# 28. Intent Classification

Implement two levels.

## Level 1 — Deterministic signals

```text
number of images
presence of before/after
presence of optical + SAR
keywords
metadata
```

## Level 2 — LLM planner

Use the LLM for ambiguous natural-language requests.

Example:

```text
2 images + "what changed"
→ bi_temporal_change

1 image + "where is the runway"
→ grounding

optical + SAR + question
→ optical_sar_fusion
```

This gives you reliability even if the LLM planner is unavailable.

---

# 29. LLM Provider Abstraction

Do not scatter Gemini API calls throughout the code.

Create:

```python
class LLMProvider:

    def generate_plan(self, request):
        raise NotImplementedError
```

Provider:

```python
class GeminiProvider(LLMProvider):
    ...
```

Fallback:

```python
class FallbackPlanner(LLMProvider):
    ...
```

The rest of the application only knows:

```python
planner.generate_plan(request)
```

This makes the backend provider-independent.

# 30. LLM Quota / Rate Limit Handling

Flow:

```text
Primary provider
       ↓
 success → continue

 failure
       ↓
 classify error
       ↓
 rate-limit?
       |
      YES
       ↓
 retry with backoff
       ↓
 still unavailable?
       ↓
 fallback provider
       ↓
 fallback unavailable?
       ↓
 deterministic router
```

Use bounded retries.

Example:

```text
attempt 1
wait 1 sec

attempt 2
wait 2 sec

attempt 3
wait 4 sec

fallback
```

Never retry indefinitely.

# 76. Final Rule for the Backend Team

Every time someone says:

> "Let's add this feature."

Ask:

### 1. What problem does it solve?

### 2. What input does it require?

### 3. Which model/tool executes it?

### 4. What exact output does it produce?

### 5. How do we validate that output?

### 6. What evidence can we show?

### 7. How do we measure its quality?

### 8. What happens if the model fails?

### 9. Can the agent select it automatically?

### 10. Can we reproduce the result?

If these ten questions cannot be answered, the feature is not finished.
